## 1. Executive Summary

This report documents the empirical evaluation and performance benchmark of the **Gargoyle Machine Learning Abuse Detection Model** compared against traditional **static rule-based API gateway heuristics**.

Rather than serving predictions over a network service, the Gargoyle ML pipeline exports a compact ONNX model (`abuse_model.onnx`) that runs **in-process inside the Go API gateway** with sub-millisecond latency and zero live Python dependencies.

### Primary Benchmark Finding
When evaluated on a real simulator dataset of **5,000 HTTP requests** generated by the Go gateway simulator ([`data/raw/ground_truth_5k.csv`](data/raw/ground_truth_5k.csv)):
* **Static Rule-Based Detection Fails on Active Users:** Static rules falsely blocked **95.0% of sustained legitimate browsing sessions** (yielding only 61.1% precision).
* **Gargoyle ML Eliminates False Alarms:** The trained Random Forest classifier achieved **100.0% precision with 0 false positives**, completely eliminating customer lockouts while maintaining a **100.0% detection rate (recall)** across brute-force, directory enumeration, and rate flooding attacks.

## 2. Why Static Rules Fail: Analysis of Gateway Failure Modes

API gateways traditionally enforce security and abuse policies using one-dimensional static thresholds:
* *Rate Limit:* $\text{Requests in 60s} > 100 \implies \text{Block}$
* *Auth Failure Limit:* $\text{401/403 errors in 5m} > 10 \implies \text{Block}$
* *Header Regex:* $\text{Missing standard browser headers} \implies \text{Block}$

While effective at catching unsophisticated volumetric floods, static rules exhibit three fundamental architectural flaws:

```
                          STATIC RULE vs. ML DECISION BOUNDARY
                          
       Requests/60s
           ^
       120 |      STATIC RULE THRESHOLD (100 req/60s)
           |-----------------------------------------------------> (Blocks everything above line!)
       100 |         x (Active Real User - BLOCKED!)       * (Bot Flood - BLOCKED)
           |
        80 |                                               * (Credential Stuffing)
           |
        60 |
           |                                               * (Low-and-Slow Attack - MISSED!)
        40 |         x (Normal User)
           |
         0 +-----------------------------------------------------> Timing Variance
                     High (Human: ~230ms)         Low (Bot: ~1ms)
```

### 1. The Power User / SPA Trapping (High False Positive Rate)
Modern web applications and power users frequently execute dozens of asynchronous API requests per minute during natural browsing (e.g., dynamic page rendering, asset loading, search autosuggest, dashboard polling). When active navigation reaches $> 100\text{ req/min}$, static rate limiters blindly flag the session as an abusive DoS attack, returning `429 Too Many Requests` to paying customers.

### 2. Blind Spot for Low-and-Slow Attacks (Evasion)
Adversaries who throttle their attack frequency just below static limits (e.g., 30–50 requests/min) bypass rate limiters entirely. Static counters reset periodically, leaving low-frequency credential stuffing and sensitive endpoint enumeration completely undetected.

### 3. Inability to Model Multivariate Correlations
Static heuristics evaluate metrics in isolation (`if Rate > X OR Fails > Y`). They cannot express non-linear relationships such as:
$$\text{Allow if: } (\text{Rate} > 100) \land (\text{Timing Variance} \ge 200\text{ms}) \land (\text{Auth Failures} = 0) \land (\text{Anomaly Score} = 0.0)$$

## 3. The 6-Feature Continuous Specification (Spec v1.0.0)

To resolve these failure modes, the Gargoyle gateway extracts a compact 6-dimensional continuous feature vector over sliding time windows (60s and 5m):

| Index | Feature Name | Data Type | Value Bounds | Cold Start | Behavioral Rationale |
| :---: | :--- | :---: | :---: | :---: | :--- |
| **0** | `requests_last_60s` | `float32` | $[1.0, \infty)$ | `1.0` | Short-term request velocity in trailing 60s sliding window |
| **1** | `avg_interval_ms` | `float32` | $[0.0, 60000.0]$ | `0.0` | Mean inter-request interval (ms) in trailing 60s window |
| **2** | `interval_stddev_ms` | `float32` | $[0.0, 60000.0]$ | `0.0` | **Timing variance** (Programmatic loops have $\sigma \approx 0\text{ms}$; humans have $\sigma > 150\text{ms}$) |
| **3** | `distinct_endpoints_last_5m` | `float32` | $[1.0, \infty)$ | `1.0` | Endpoint diversity (Distinguishes directory scrapers from normal users) |
| **4** | `failed_auth_count_last_5m` | `float32` | $[0.0, \infty)$ | `0.0` | Rolling auth failure count (Detects credential stuffing / brute force) |
| **5** | `header_anomaly_score` | `float32` | $[0.0, 1.0]$ | `0.0` | Heuristic score reflecting missing or spoofed HTTP browser headers |


* **Static Rule Decision:** `requests_last_60s (101) > 100` $\implies$ **BLOCKED (False Alarm)**

## 8. Gateway Runtime Integration (Phase 6)

### Integration Workflow
1. **Model Loading:** The Go gateway (`gargoyle`) initializes an in-process ONNX Runtime session using `models/abuse_model.onnx` at server startup.
2. **Feature Computation:** For each incoming HTTP request, Go's sliding-window history tracker computes the 6 continuous float features in the exact spec order.
3. **Inference:** Go executes `session.Run()` passing the `float32[1, 6]` tensor into the model.
4. **Scoring & Enforcement:**
   - $P(\text{Abuse}) < 0.5$: Request is treated as legitimate and proxied to upstream services.
   - $P(\text{Abuse}) \ge 0.5$: Request is flagged, logged, or rejected with `429 Too Many Requests` depending on the gateway's configured enforcement mode.

### Zero-Drift Guarantee
Cross-language parity is continuously verified by [`export/parity_check.py`](export/parity_check.py) and [`tests/test_parity.py`](tests/test_parity.py) using canonical test fixtures in [`fixtures/parity_fixtures.json`](fixtures/parity_fixtures.json), guaranteeing that Python training and Go runtime inference yield identical feature vectors and classification scores.
