## 1. Executive Summary

Gargoyle ML provides an offline training and export pipeline that produces a portable machine learning model (`abuse_model.onnx`) consumed by the Gargoyle Go API Gateway. Rather than replacing the gateway's rule-based heuristic engine, the machine learning model operates as an intelligent, complementary scoring layer.

The ML scorer runs **in-process within Go** with zero runtime Python dependencies, providing sub-millisecond abuse likelihood scoring on live HTTP traffic.

### Key Finding
Evaluating against **5,000 real simulator requests** ([`data/raw/ground_truth_5k.csv`](data/raw/ground_truth_5k.csv)) demonstrated that **static rule-based detection falsely blocks 95.0% of sustained legitimate user sessions** (61.1% precision). In contrast, the **Gargoyle ML model achieves 100.0% precision with 0 false positives**, eliminating customer disruption while detecting 100% of brute-force, directory scanning, and rate-flooding attacks.

## 2. The Core Problem: Why Static Rules Fail

Rule-based abuse detection in API gateways relies on static, one-dimensional thresholds (e.g., *TokenBucket rate limit > 100 req/60s*, *Failed auth > 10 fails/5m*, *Suspicious User-Agent check*).

While static rules catch crude attacks, they suffer from two critical architectural failure modes:

1. **High False Positive Rate on Active Legitimate Users (The Power User Problem):**
   Modern Single-Page Applications (SPAs) and active users regularly trigger multiple parallel API calls (e.g., page loads, search queries, cart updates, background polling). When sustained browsing reaches $>100\text{ req/min}$, static rules blindly flag the user as an abusive DoS bot, returning `429 Too Many Requests`.
2. **Blind Spot for Low-and-Slow Attacks:**
   Attackers who throttle their request rates just beneath static thresholds (e.g., 30–50 req/min) operate completely undetected by rate limiters.
3. **Inability to Model Multivariate Correlations:**
   Static rules evaluate features in isolation (`if Rate > X OR Fails > Y`). They cannot express non-linear relationships such as: *"High request rate is acceptable IF AND ONLY IF inter-request timing variance is high (human-like) AND auth failures are zero."*

## 3. The Gargoyle 6-Feature Specification (Spec v1.0.0)

To resolve these limitations, Gargoyle computes a compact, 6-dimensional continuous feature vector extracted over sliding time windows:

| Index | Feature Name | Data Type | Bounds | Cold Start | Description |
| :---: | :--- | :---: | :---: | :---: | :--- |
| **0** | `requests_last_60s` | `float32` | $[1.0, \infty)$ | `1.0` | Request volume in trailing 60s sliding window |
| **1** | `avg_interval_ms` | `float32` | $[0.0, 60000.0]$ | `0.0` | Mean time interval between requests in 60s window |
| **2** | `interval_stddev_ms` | `float32` | $[0.0, 60000.0]$ | `0.0` | **Timing variance** (Low = automated bot; High = human) |
| **3** | `distinct_endpoints_last_5m` | `float32` | $[1.0, \infty)$ | `1.0` | Unique normalized URI endpoints accessed in trailing 5m |
| **4** | `failed_auth_count_last_5m` | `float32` | $[0.0, \infty)$ | `0.0` | HTTP 401/403 failure count in trailing 5m |
| **5** | `header_anomaly_score` | `float32` | $[0.0, 1.0]$ | `0.0` | Heuristic penalty score from Go's rule layer |

## 6. Concrete Case Studies & Examples

### Case Study 1: The Active Legitimate User (Why Rules Cause False Alarms)

Consider a legitimate human user actively browsing an e-commerce site for 60 seconds. At request #101, their sliding window state is:

```
requests_last_60s:          101.0
avg_interval_ms:            218.5 ms
interval_stddev_ms:         235.4 ms   <-- Natural human timing variability
distinct_endpoints_last_5m: 9.0        <-- Varied navigation (/products, /search, /cart)
failed_auth_count_last_5m:  0.0        <-- Clean authentication history
header_anomaly_score:       0.0        <-- Legitimate Chrome browser headers
```

* **Static Rule Decision:** `requests_last_60s (101) > 100` $\implies$ **BLOCK (False Alarm)**  
  *Impact:* Legitimate paying customer is blocked from the platform.
* **ML Model Decision:** Observes high timing variance ($235.4\text{ms}$), 0 auth errors, and clean headers $\implies$ **ALLOW (Abuse Probability: `0.00`)**  
  *Impact:* Legitimate user continues uninterrupted.

## 8. Deployment & Architectural Invariants

1. **Zero Runtime Python Dependency:**  
   Python is strictly an offline training and export environment. The Go gateway loads `abuse_model.onnx` at startup and executes inference in-process via ONNX Runtime.
2. **Feature Parity Invariant:**  
   The feature extraction order in Go's `MLScorer` must match [features/feature_spec.md](features/feature_spec.md) identically:
   `[requests_last_60s, avg_interval_ms, interval_stddev_ms, distinct_endpoints_last_5m, failed_auth_count_last_5m, header_anomaly_score]`
3. **Graceful Fallback:**  
   If the ONNX model is missing or corrupted, Go logs a warning and falls back to rule-based detection without interrupting proxy traffic.
